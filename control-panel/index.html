    Live feed and your own overlays
    
      
    
        Every graphic in this app is an ordinary web page reading one live state feed over a WebSocket.
        Your own pages can read exactly the same feed — point an OBS browser source at any HTML file you
        host and it gets the same teams, scores, brackets, casters and timers the built-in overlays use.
        The feed is read-only: production stays under producer control.
      
    

      
    1. Connect
    
      
    
        WebSocket on ws://127.0.0.1:3001, HTTP API on http://127.0.0.1:3000.
        Use the machine's LAN address instead of localhost to run a source from another PC.
        Fetch a token from GET /api/ws-token and pass it as ?token=.
      
    

      
    2. Handshake
    
      
    
        Send { type: 'register', role: 'overlay', page: '/your-page.html' } so the app's
        pre-flight check can see your source, then { type: 'request_state' } for a snapshot.
      
    

      
    3. Merge — do not replace
    
      
    
        The one thing that catches everybody. State travels in two tiers. Your reply to
        request_state is the complete picture (live + library: team logos, brackets, clips,
        leagues). Every broadcast after that reuses the same full_state message type
        but carries only the small live tier — the heavy library keys are simply absent,
        and are re-sent only when they change. So merge each payload into your own copy
        (Object.assign). Assigning state = msg.data works for about one second,
        then your logos and bracket vanish on the first score update.
      
    

      
    4. Images
    
      
    
        Logos arrive as ordinary data URLs. The compact "@img:<hash>" reference form is
        strictly opt-in (overlays send imgvault_ready to trade repeated base64 for hashes on
        busy shows) — if you never opt in, you never have to resolve them.
      
    

      
    Minimal working source
    
      
    const state = {};                       // your own merged copy

async function connect() {
  const { token } = await fetch('http://127.0.0.1:3000/api/ws-token').then(r => r.json());
  const ws = new WebSocket('ws://127.0.0.1:3001?token=' + encodeURIComponent(token));

  ws.onopen = () => {
    ws.send(JSON.stringify({ type: 'register', role: 'overlay', page: '/my-overlay.html' }));
    ws.send(JSON.stringify({ type: 'request_state' }));   // one full snapshot
  };

  ws.onmessage = ({ data }) => {
    const msg = JSON.parse(data);
    if (msg.type !== 'full_state') return;
    Object.assign(state, msg.data);      // MERGE — never `state = msg.data`
    render(state);
  };

  ws.onclose = () => setTimeout(connect, 1000);   // browser sources must self-heal
}

function render(s) {
  document.body.textContent =
    (s.teams?.blue?.name ?? '') + ' ' + (s.series?.blue ?? 0) +
    ' - ' + (s.series?.orange ?? 0) + ' ' + (s.teams?.orange?.name ?? '');
}

connect();
    

      
    Pushing live data in
    
      
    
        Two write endpoints exist for live scoring. Both accept JSON and return
        { ok: true }. /api/bedwars is the one a server admin implements —
        Minecraft is scored by the server, so a Spigot/Paper plugin is the authoritative source. Send
        the full team list on every post (it replaces the previous snapshot); events is a
        delta and each entry fires a Flow trigger.
      
    
      
    POST /api/bedwars
Content-Type: application/json
X-Suite-Token: <token from Integrations › Games & GSI › Bedwars>   // omit if none set

{
  "teams": [
    { "key": "red",  "name": "Red",  "bedAlive": true,  "players": 4, "eliminated": false },
    { "key": "blue", "name": "Blue", "bedAlive": false, "players": 2, "eliminated": false }
  ],
  "events": [
    { "type": "bed_break",       "team": "blue", "by": "Steve" },
    { "type": "final_kill",      "by": "Steve",  "victim": "Alex" },
    { "type": "team_eliminated", "team": "blue" }

        timer; there is no polling and no minimum interval.

        companion rather than written by hand — see Integrations › Games & GSI.

          Build show scenes
          
    Adds NE In Game, Starting Soon, Casters, Replay, Post-Game, Bracket and Commercial to the scene collection you
            already use, each sized to your canvas. Nothing of yours is changed; running it again only refreshes them.
    
          
    What goes in them?
    
            Every show is built on two sources: NE Scoreboard (live.html, the HUD of the game set in
            this app) and NE Graphics (gfx.html, everything you put on air from Graphics, always on top).
            Afterwards put your game capture under NE Scoreboard in NE In Game. The automatic cuts
            point at the new scenes wherever you have not picked one yourself. vMix: they are added as Web Browser
            inputs, NE Graphics goes on overlay channel 4 and NE Scoreboard is layered onto your In Game input.
          
    
          
        
    
        
    
          Full scene collection OBS, advanced
          
    A ready-made OBS scene collection: 32 scenes (pre-game, game HUDs, desk and caster layouts, post-game) plus cam
            framing scenes. Import it in OBS with Scene Collection → Import.
    
          
    Before you import
    
            Saved as NE Broadcast Suite.json (your OBS scenes folder if found). Each caster slot is a permanent
            browser source (castercam.html?slot=N) that follows the caster assignments here, with its own audio
            fader. Re-importing resets any changes you made in OBS to this collection.
